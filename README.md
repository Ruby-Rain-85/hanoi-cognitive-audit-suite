# Hanoi Cognitive Audit Suite: Benchmarking Recursive Planning and State-Space Integrity in LLMs

A deterministic benchmarking and validation framework designed to audit Large Language Model (LLM) performance on recursive planning, long-horizon state tracking, and physical constraint adherence using the Tower of Hanoi problem.

---

## 1. Project Inspiration & Research Motivation

This project emerged from ongoing debates regarding the depth of symbolic and mathematical reasoning in Large Language Models (LLMs), notably highlighted by Apple's 2024 research on the limitations of formal reasoning in autoregressive architectures (GSM-Symbolic). While frontier models demonstrate convincing linguistic fluency, questions remain regarding whether they maintain internal state models or merely execute surface-level pattern replication.

Initial exploratory tests on GPT-4o and Claude Sonnet showed unexpected resilience on basic Tower of Hanoi sequences. However, scaling the problem to an 8-disk configuration ($2^8 - 1 = 255$ transitions) revealed immediate bottlenecks in token budget and long-horizon context retention. To mitigate token consumption and eliminate conversational drift, the output schema was constrained to a structured, tabular transition log.

Manual auditing of 255 discrete states demonstrated that human verification does not scale reliably to large state spaces. To establish rigorous academic ground truth, this project created an external, deterministic Python verification oracle. The oracle audits action legality independently of model claims, enabling reproducible benchmarks on recursion, heuristic bias, and error recovery across multi-model iterations.

This project originated from a simple question: **When an LLM attempts a recursive sequence, does it maintain a true structural state space, or does it suffer from heuristic drift and hallucinated legal transitions?** 

By building an external, deterministic Python verification oracle, this suite decouples the model's textual output from the ground truth. It converts text generation into verifiable state-space transitions, providing quantitative metrics on model accuracy, rule violations, and in-context adaptation.

## 2. Theoretical Background & Complexity Invariants

The Tower of Hanoi serves as a classic benchmark for recursion, state-space search, and mathematical induction.

* **Optimal Step Bound:** For a puzzle with $n$ disks, the minimal sequence of moves required to reach the goal state is defined by the recurrence relation:
  $$M(n) = 2M(n-1) + 1$$
  which yields the exponential closed-form solution:
  $$M(n) = 2^n - 1$$
* **Physical Game Invariants:**
  1. Only one disk may be moved per discrete time step.
  2. Only the top (exposed) disk of a source rod can be removed.
  3. A disk may never be placed on top of a smaller disk.
  4. Disks cannot be transferred to the identical rod.

For the primary baseline evaluated in Iteration 1 ($n = 8$ disks), an optimal algorithmic trajectory requires exactly $2^8 - 1 = 255$ moves.

## 3. Architecture & Verification Engine

The verification engine does not rely on visual peg printouts generated by the model. Relying on model-generated peg states introduces confirmation bias, as models frequently hallucinate legal board states in text while executing illegal moves under the hood.

Instead, the Python audit engine (`verify_hanoi.py`) operates as an independent state machine:
1. **State Initialization:** Peg 1 is populated with an ordered array representing disks `1` through `8`, while Pegs 2 and 3 are initialized empty.
2. **Action Ingestion:** The engine reads only the action columns (`From`, `To`, `Disk`) per row.
3. **Constraint Gating:** Each move must pass boundary, emptiness, exposed-disk, and size-ordering checks.
4. **State Transition:** Upon passing all checks, the top disk is moved via atomic list operations (`pop(0)` and `insert(0)`).
5. **Human Baseline Reconciliation:** If a `Human Check` column is detected, the engine cross-references the programmatic verdict against human labels, flagging discrepancies.

## 6. Multi-Iteration Research Roadmap

Future iterations expand this testbed beyond static single-model audits into a comparative multi-agent benchmarking suite:

* **Iteration 2: Multi-Model Comparative Benchmarking**  
  Deploy the oracle across multiple model families and parameter scales (such as Claude, Llama 3, Gemini, and GPT-4o) to compare error distributions.
* **Iteration 3: Heuristic Drift & Directional Bias Analysis**  
  Analyze token-frequency bias and directional peg preference (such as systematic bias toward Peg 2 over Peg 3) under non-standard starting conditions.
* **Iteration 4: In-Context Error Recovery and Adaptation Velocity**  
  Feed execution failure messages directly back into the model prompt to benchmark how rapidly models recover from invalid states without human intervention.
* **Iteration 5: Cross-Model Review Dynamics**  
  Evaluate models tasked with auditing other models' move sequences, comparing secondary model judgments directly against the deterministic Python ground truth. 

## Model Prompting Protocol for Experimental Replication

To ensure uniform column and row structures that align with the `verify_hanoi.py` validation engine, all model interactions must use the standardized prompt structure below.

### System Prompt
```text
You are a deterministic logic engine solving the Tower of Hanoi puzzle.
You must output only a valid sequence of moves in an excel spreadsheet.
Do not provide introductory text, explanations, or commentary outside the table.
Solve the Tower of Hanoi puzzle for 8 disks.
Goal: Move all 8 disks from Peg 1 to Peg 3 using Peg 2 as an auxiliary peg.

Formatting Constraints:
1. Provide exactly 7 columns with these exact headers:
   "Move #", "Disk", "From", "To", "Peg 1", "Peg 2", "Peg 3"
2. Disks are integers from 1 (smallest) to 8 (largest).
3. Peg identifiers must be integers: 1, 2, or 3.
4. "Peg 1", "Peg 2", and "Peg 3" must state the complete configuration of disks on that peg immediately after each move completes.
5. Format disk lists as comma-separated integers inside brackets, ordered from bottom to top (e.g., [2, 3, 4, 5, 6, 7, 8]).
6. If a peg is empty, format it strictly as [].
7. Output the full optimal sequence of discrete moves without truncation.
```
